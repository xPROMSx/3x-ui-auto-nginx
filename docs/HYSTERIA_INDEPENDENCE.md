# REALITY/Hysteria2: Disable/Enable перед внедрением

Продолжение исследования PR #99 от `ebc72d0bddd291b36efb704f79dd244c743a0e3c`.
Исполняемый установщик и публичная привязка Hysteria2 **не изменены**.
Проверки выполнены в одноразовом Ubuntu 24.04-контейнере на настоящих
3x-ui v3.11.0, Xray 26.10.21 и Nginx 1.24.0. Полный Fresh не запускался;
завершённые 83/93 HTTP-пробы не повторялись.

## Резервный маршрут

Без backup отключение REALITY закрывает 8443: HTTPS на её домене перестаёт
работать, хотя Hysteria2 и её статический Unix HTTP/3-backend продолжают работать.
Это реальный риск предложенной смены привязки Hysteria2 на REALITY-домен.

Предложение с обычным `backup` сохраняет HTTPS, но после включения REALITY
primary остаётся временно исключённым. Настоящий REALITY-клиент не подключается
сразу; после окончания стандартного fail_timeout (около 10 секунд) подключается.
Эффект воспроизведён отдельно от переключений самой панели.

Минимальный проверенный вариант:

```nginx
upstream xray {
    server 127.0.0.1:8443 max_fails=0;
    server 127.0.0.1:9443 backup;
}
```

`max_fails=0` убирает пассивный карантин primary. При отказе локального connect
текущий запрос идёт на backup; следующий снова пробует primary. Никакого
монитора, общего состояния или нового listener нет. 9443 — прежний статический
REALITY HTTPS fallback, уже принимающий PROXY protocol. Вариант относится
к этому известному layout (`xver=1`); старый `xver=0` без PROXY на 9443
не переписывается и не получает backup автоматически.

## Нативные переключения

Использован именно `POST /panel/api/inbounds/setEnable/:id`, как в штатной панели,
а не редактирование SQLite или полный `update/:id`. Последний не заменяет
специализированный toggle. В транспортный fixture возвращён штатный локальный
Handler API Xray из нативного шаблона панели. Два клиента созданы настоящим API
проекта/панели, включая клиентские привязки и runtime cache. Прямой SQL seed
клиентов исходного transport-only fixture не использовался для hot-enable.

| REALITY | Hysteria2 | 8443 / UDP 443 | Клиенты | HTTPS TCP | HTTP/3 | Старый runtime gate |
| --- | --- | --- | --- | --- | --- | --- |
| ON | ON | Есть / есть | Оба работают | 200 | 200 | PASS |
| OFF | ON | Нет / есть | REALITY недоступен, HY работает | 200 | 200 | FAIL |
| ON | OFF | Есть / нет | REALITY работает, HY недоступен | 200 | Недоступен | FAIL |
| OFF | OFF | Нет / нет | Оба недоступны | 200 | Недоступен | FAIL |

Проверены девять последовательных состояний с повторными OFF/ON, без ручного
исправления Nginx и без принудительного Restart Xray между переключениями.
PID ядра сохранился. Дополнительно уже открытый TCP-канал через Hysteria2
пережил повторные отключения/включения REALITY, а канал REALITY — переключения
Hysteria2. Это реальная передача случайных payload через отдельный loopback echo
origin, а не проверка текста конфигурации.

Нативные RAW и JSON исключают отключённые inbounds и возвращают их после Enable:
5 → 4 → 3 профиля в этом fixture. Идентичность соседнего клиента и его реальные
подключения после переключений сохранены. Пользователи, клиенты, привязки,
прочие inbounds/настройки не менялись; штатные счётчики трафика не считаются
изменением идентичности. Сертификаты и оба сайта побайтово сохранены.

Отключённый XHTTP проверен отдельно: его Unix listener закрывается, REALITY
и Hysteria2 работают, но тот же старый runtime gate возвращает FAIL. Последующее
включение восстанавливает Unix listener.

## Безопасность

В обоих путях — через Xray и напрямую через backup — посетитель `127.0.0.2`
остаётся `127.0.0.2` в trusted PROXY chain. Поддельные X-Real-IP/X-Forwarded-For
не подменяют адрес. Неподтверждённый PROXY prelude на публичном TCP/443 не получает
успешного TLS-соединения. Неправильный Host получает 404; неправильный SNI
с правильным Host — 421 в намеренно атакующей TCP-пробе. Нормальные клиенты
проверяют сертификат; Hysteria2 сохраняет строгий SNI и авторизацию.

Резерв указывает только на 9443, не на 7443. Панель и диагностика через этот
путь недоступны. Unix HTTP/3-vhost остаётся статическим. Новых публичных портов,
сертификатов, служб, доверия к административным IP-заголовкам или копий сайта нет.

## Эксплуатационные зависимости: прежнее и новое

### Check Installation и Change Domains

`check_xray_runtime()` в установщике безусловно пересекает владельцев трёх
listeners: REALITY TCP, XHTTP Unix и Hysteria2 UDP. Его выполнение на настоящих
listeners подтвердило FAIL при штатном Disable любого из них. Проверялись
настоящие `ss` и `/proc`; только `systemctl is-active` в этом вызове заменён
подтверждением активности запущенной панели, поскольку PID 1 не systemd. Это существующий
строгий full-install gate, не дефект Unix proxy.

`check_installation()` вызывает его последним. Change Domains использует тот же
health callback в `Operation.healthy()` **до Backup, Certbot, журнала и SQLite
изменений**. Поэтому Panel only, REALITY only и Both сейчас блокируются таким
отключением; никакого скрытого Enable не происходит. Здоровый статический
backup-сайт сам по себе этого не исправляет. Здесь речь о прежнем поддерживаемом
Panel layout. Исследуемый REALITY prototype с новым upstream пока вообще
не распознаётся действующим Change Domains и безопасно отклоняется ещё при
проверке identity/layout; это отдельная необходимая часть будущей реализации.

Отдельно проверены девять сочетаний отключённых ролей и Panel/REALITY/Both на
настоящих scoped SQL edits Change Domains: `enable=0`, клиенты и привязки
сохраняются. Это проверка слоя SQLite, **не заявление об успешной полной операции
при нынешнем health gate**. Удаление обязательной роли по-прежнему должно давать
безопасный отказ; Disable не должен трактоваться как удаление.

Минимальное исправление для следующей реализации: maintenance-health должен
читать `enable` известных присутствующих ролей из SQLite и проверять ожидаемые
listeners/PID, не включать роль сам. Строгий fresh-install gate сохраняется.
Generated `bin/config.json` не подходит как источник enable после hot API.
Для старого stream layout нельзя требовать публичный REALITY HTTPS при Disable,
когда он заведомо недоступен; остальные TLS/config/ownership проверки сохраняются.
Для нового layout с backup статический HTTPS должен проверяться даже при OFF.
Произвольные модификации, отсутствующие роли и неизвестные upstream не принимаются.

### Backup/Restore v3

В нынешнем Restore v3 итоговый `check_health()` проверяет сохранённые состояния
служб, Nginx, панель и SQLite; приведённый безусловный transport gate там не
вызывается. Отдельные существующие root-тесты Backup, Restore и rollback
подтвердили сохранение отключённых transports и неизменность исходного архива.
Это реальные файловые/SQLite/архивные fixtures с контролируемыми системными
службами — **PARTIAL Restore**, не полный disaster recovery VPS.

Формат v3 и TREE_PATHS не требуют изменения. Новые Nginx backup/Unix файлы и
привязка Hysteria2 ещё должны пройти полный Restore после принятия реализации.

### Рестарты, сертификаты и reboot

Настоящие процессы панели/Xray и Nginx полностью остановлены/запущены в состояниях
OFF/ON, ON/OFF и OFF/OFF. Флаги сохранились; ожидаемые clients/listeners и HTTPS
вернулись, Unix backend пересоздался, HTTP/3 при HY ON работает. Затем оба
транспорта включены штатным API и оба клиента снова передают данные.

Текущий canonical deploy hook проверен существующим decision-matrix тестом:
Panel renewal → Nginx reload и try-restart x-ui, REALITY renewal → только reload
Nginx. В нём нет безусловного transport gate. Старые поддерживаемые варианты
hook с `check_xray_runtime()` могут дать FAIL при Disable; это отдельное прежнее
ограничение, не повод автоматически переписывать VPS.

Для предлагаемой REALITY-привязки нужно явно обеспечить обновление TLS Hysteria2
при renewal REALITY. По текущему исходнику Xray `oneTimeLoading=false` обновляет
файловый сертификат с интервалом 3600 секунд при `ocspStapling=0`; нельзя считать
reload Nginx немедленным обновлением сертификата Xray. Достаточен существующий
механизм restart x-ui в правильном deploy hook, без изменения enable.

**NOT RUN:** реальный reboot VM/VPS и полное Certbot renewal с комбинациями
Disable/новым REALITY layout. Локальный стенд контейнерный, без systemd PID 1
и готовой VM. Процессный restart не объявляется reboot. Полноценную проверку
холодной загрузки следует добавить в существующую cold-boot фазу окончательного
Fresh после внедрения: Disable перед загрузкой, проверить флаги/сайт, затем
нативный Enable и штатные cold transport consumers. Новый workflow не нужен.

## Рекомендуемый итоговый вариант

Сохранить предложение REALITY Unix proxy и добавить только проверенный
`max_fails=0` + backup 9443. [Не применённый diff ядра](HYSTERIA_REALITY_PROPOSAL.patch)
обновлён; он не является готовой установкой и не применяется к существующим VPS.
Публичная привязка по-прежнему требует отдельного подтверждения владельца.

Затрагиваются: известный stream layout/его bounded распознавание Change Domains,
Host/SNI/TLS Hysteria2, static Unix vhost, certificate hook, maintenance health,
scoped доменные операции и адресные Backup/Restore/boot тесты. Vision сохраняет
ту же map anchor и порты; универсальный stream parser не предлагается.

Panel Unix proxy дешевле и не требует backup ради собственного TCP-прикрытия.
Но он сохраняет известное расхождение TCP `/assets` с HTTP/3 и **не устраняет**
существующее ограничение maintenance-health при Disable. Проверенный backup
не показал ненадёжности, требующей отказаться от REALITY в пользу Panel.

## Воспроизведение

На прежнем одноразовом nonroot стенде исследования (не на VPS):

```bash
HY_EXPERIMENT_MODES=independence NGINX_BIN=/usr/sbin/nginx \
  PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=tests python3 tests/hysteria_cover_probe.py
```

Источник API проверен по `internal/web/controller/inbound.go` и
`internal/web/service/inbound.go` официального v3.11.0. Исполняемые файлы проходят
прежние проверки baseline. Приватные логи, клиентские значения и тела подписок
не публикуются. Merge, release, production и Rulesets не затрагивались.
