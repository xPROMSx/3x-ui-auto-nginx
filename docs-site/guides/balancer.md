# Резервный зарубежный сервер: балансировщик для каскада

**Создано:** 23 ноября 2026 года.

**Актуально для:** 3X-UI AUTO NGINX **v2.8.0**, панели **3x-ui v3.11.0** и Xray **26.10.21**. Названия элементов и поведение проверялись по исходникам указанных версий; фактическое переключение на двух VPS необходимо проверить в своей сети.

## Зачем это нужно и какой будет результат

Предположим, у тебя уже работает [каскад из двух VPS](cascade.md): устройства подключаются к российскому серверу, а он отправляет выбранный трафик через сервер в Финляндии. Если зарубежный сервер перестанет отвечать, зависимый от него маршрут перестанет работать.

Можно добавить **третий VPS**, например в Швеции, и настроить **резервирование**: пока основной выход в Финляндии доступен, использовать его; когда проверка обнаружит недоступность, новые соединения направлять через Швецию.

```text
Телефон → Входной VPS в России → правила маршрутизации
                                      │
                                      ▼
                               Балансировщик
                                      │
                     ┌────────────────┴───────────────┐
                     ▼                                ▼
             Основной: Финляндия              Резерв: Швеция
                 cascade-exit                    backup-se
                     │                                │
                     └────────────► Интернет ◄────────┘
```

После инструкции **клиентские профили и подписки менять не нужно**: выбор выходного сервера делает Xray на российском VPS. Российские исключения каскада останутся такими, какими ты их настроил.

Ты также научишься отличать резервирование от обычной балансировки, проверять наблюдателя (Observatory), вручную тестировать резерв и возвращаться к исходной конфигурации.

## 1. Чем резервирование отличается от балансировки

**Исходящее подключение (outbound)** - готовый путь с VPS к интернету или другому серверу. **Балансировщик (balancer)** - объект с собственным тегом, который выбирает один из исходящих. **Правило маршрутизации** определяет, когда этот балансировщик использовать.

В 3x-ui доступны стратегии:

| Стратегия | Для чего подходит |
| --- | --- |
| `Random` | Случайно распределять новые соединения между кандидатами |
| `Round robin` | Выбирать кандидатов по очереди |
| `Least ping` | Выбирать живой выход с наименьшей измеренной задержкой |
| `Least load` | Выбирать по результатам более сложных проб и оценке загрузки |

Для нашей цели важны ещё два поля:

- **Selector** - кандидаты, среди которых стратегия делает обычный выбор. **В него добавим только основной `cascade-exit`.**
- **Fallback** - резервный исходящий, который Xray выберет, если стратегия не смогла выбрать ни одного кандидата. **В него добавим `backup-se`.**

**Почему не поместить оба сервера в Selector?** Тогда `Least ping` сможет выбрать Швецию просто потому, что сейчас её задержка меньше, даже если Финляндия полностью исправна. Мы хотим другой результат: Финляндия **приоритетна**, Швеция нужна **при её отказе**.

Стратегия `Least ping` использует результаты наблюдателя. Если основной выход помечен как недоступный, выбор кандидата окажется пустым и включится Fallback. Это **не переключение без единого потерянного пакета**: уже открытые соединения могут оборваться, а обнаружение отказа занимает время.

## 2. Что должно быть подготовлено

1. На российском VPS работает [каскад](cascade.md) и есть исходящее `cascade-exit` к основному зарубежному VPS.
2. Ты добавил резервный зарубежный сервер по инструкции [«Импорт VLESS REALITY»](import-reality.md) и назвал новый исходящий `backup-se`.
3. В разделе **Xray → Исходящие** оба маршрута проходят **HTTP-тест** по отдельности.
4. В разделе **Xray → Маршрутизация** есть правило `CASCADE - EXIT`, которое сейчас указывает прямо на `cascade-exit`.

Пока эти четыре пункта не выполнены, балансировщик создавать рано. Наличие резервного исходящего без работающего REALITY-подключения не защитит от отказа основного.

!!! warning "Сохрани рабочее состояние"
    Сделай резервную копию конфигурации до изменений. На работающем сервере изменение правил может временно прервать соединения. Не удаляй исходящие `cascade-exit` и `direct`, клиента `cascade` или служебные правила панели.

## 3. Создай балансировщик

Все дальнейшие действия выполняются **в веб-панели российского входного VPS**.

1. Открой **Xray → Балансировщики**, вкладку **«Настройки балансировщика»**.
2. Нажми **«+ Балансировщик»**.
3. В поле **«Тег»** введи `cascade-failover`. Это имя нового балансировщика, не адрес VPS.
4. В поле **«Стратегия»** выбери **Least ping**.
5. В поле **«Селектор» (Selector)** выбери **только `cascade-exit`** - основной сервер в Финляндии.
6. В поле **Fallback** выбери **`backup-se`** - резервный сервер в Швеции.
7. Нажми **«Создать»**.

В списке должна появиться строка:

| Tag | Strategy | Selector | Fallback |
| --- | --- | --- | --- |
| `cascade-failover` | `Least ping` | `cascade-exit` | `backup-se` |

**Проверь именно эти значения.** Селектор в Xray сопоставляется с префиксами тегов исходящих. Если ты создал другие исходящие с именем, начинающимся на `cascade-exit`, они тоже могут попасть в выбор. При таком совпадении сначала измени имена пользовательских выходов или уточни схему, не рассчитывай на строгое равенство.

## 4. Настрой проверку доступности: Observatory

Открой в разделе балансировщика вкладку **«Обсерватория» (Observatory)**. Панель 3x-ui автоматически создаёт и связывает наблюдателя со стратегией `Least ping`. Для обычного резервирования не нужно вручную писать JSON с наблюдателем.

Проверь:

1. **Отслеживаемые исходящие:** среди них должен быть `cascade-exit`. Он попадает сюда из Selector балансировщика.
2. **URL пробы:** например `https://cp.cloudflare.com/generate_204`. Сервер должен отвечать **HTTP 204**, а запрос должен проходить через проверяемое исходящее.
3. **Интервал пробы:** для начала `1m` - проверка примерно раз в минуту.
4. **Параллельные пробы:** можно оставить включёнными. Это позволяет проверять несколько отслеживаемых выходов одновременно.

Для выбора `Least ping` учитываются не просто результаты TCP-соединения, а сведения наблюдателя о доступности и задержке выбранных исходящих.

**Чего это не гарантирует:** успешная HTTP-проба к одному сайту не доказывает доступность всех сервисов интернета. И наоборот: сбой конкретного адреса пробы может вызвать переключение, даже если основной сервер в целом работает. Выбирай стабильный URL, реально доступный через твой зарубежный VPS.

**Резервный `backup-se` не входит в Selector, поэтому этот балансировщик не обязан заранее проверять его доступность.** До настройки Fallback обязательно проведи отдельный HTTP-тест резервного исходящего. Сам Fallback не превращает третий сервер в ещё одну автоматически проверяемую цепочку резервов.

## 5. Подключи балансировщик к маршрутизации

Это обязательный шаг. **Создать балансировщик недостаточно**: пока правило `CASCADE - EXIT` указывает прямо на `cascade-exit`, новый объект не участвует в выборе маршрута.

1. Перейди на российском VPS в **Xray → Маршрутизация**, вкладку со списком правил.
2. Найди правило **`CASCADE - EXIT`** (после российских исключений `CASCADE - RU` и `CASCADE - RU2`).
3. Нажми значок карандаша.
4. Очисти поле **«Исходящий тег» (outboundTag)**, в котором сейчас выбран `cascade-exit`.
5. В поле **«Балансировщик» (balancerTag)** выбери `cascade-failover`.
6. Не меняй условие `network: tcp,udp` и комментарий `CASCADE - EXIT`.
7. Сохрани правило, затем нажми **«Сохранить»** на основной странице Xray.

В итоге правило должно указывать на **балансировщик**, а не одновременно на исходящий тег и балансировщик.

```text
CASCADE - RU   → direct
CASCADE - RU2  → direct
CASCADE - EXIT → cascade-failover
                  ├─ Selector: cascade-exit (основной)
                  └─ Fallback: backup-se (резерв)
```

Почему мы изменяем существующее правило, а не добавляем ещё одно? `CASCADE - EXIT` уже является общим маршрутом каскада. Дублирующее широкое правило может перехватить трафик раньше нужных условий и запутать порядок.

**Российские исключения сохраняются:** `CASCADE - RU` и `CASCADE - RU2` по-прежнему отправляют подходящие запросы непосредственно с российского сервера. Если хочешь изменить это поведение или использовать резервный сервер только для определённых сайтов/клиентов, прочитай [руководство по маршрутизации](routing.md).

## 6. Проверь основной сервер и резервирование

**Проверка № 1: оба исходящих.** В разделе **Xray → Исходящие** выбери `HTTP` и кнопкой-молнией проверь `cascade-exit` и `backup-se` по отдельности. У обоих должна быть успешная проверка.

**Проверка № 2: выбранная цель.** В **Xray → Балансировщики → Настройки балансировщика** найди строку `cascade-failover`. Посмотри столбец **«Текущая цель»**. Когда основной выход доступен и уже собраны успешные пробы, ожидается `cascade-exit`.

**Проверка № 3: принудительный выбор резерва.**

1. В строке балансировщика найди **«Переопределить» (Override)**.
2. Временно выбери `backup-se`.
3. С подключённого к российскому VPS устройства открой проверку внешнего IP. Для обычного прямого выхода должен быть IP шведского VPS. Учитывай, что российские сайты всё ещё могут попадать под `CASCADE - RU` / `RU2`, а WARP на выходном сервере может менять внешний IP.
4. **Верни Override в «Авто (стратегия)».** Не оставляй принудительный выбор резерва после проверки.

Ручной Override позволяет проверить маршрут, но **не доказывает автоматическое переключение**.

**Проверка № 4: автоматический отказ и возврат.** Если у тебя есть отдельные тестовые VPS или согласованное окно обслуживания, временно сделай основной выход недоступным **без изменения SSH и без удаления сервера**. Дождись, пока Observatory покажет отказ и у балансировщика выберется Fallback. Открой тестовый ресурс через каскад и проверь внешний IP. Затем восстанови основной выход, дождись успешных проб и проверь возврат к `cascade-exit`.

На основном рабочем VPS не стоит устраивать искусственный отказ ради чтения инструкции. Без этой проверки можно утверждать только, что конфигурация сохранена и ручной выбор работает, **но не что автоматический переход уже проверен**.

## 7. Что произойдёт при настоящем сбое

- Наблюдатель периодически проверяет основной `cascade-exit`.
- Если он перестаёт считаться доступным, `Least ping` не выбирает кандидата из Selector.
- Балансировщик использует `backup-se` как Fallback **для новых соединений, попавших под правило**.
- Когда новый цикл проб подтвердит восстановление основного, стратегия снова сможет выбрать `cascade-exit`.

Переключение не мгновенное: интервал `1m` означает периодические проверки, а не обещание переключиться ровно за 60 секунд. Старые TCP/UDP-сессии могут потребовать переподключения. Если резерв тоже недоступен, работа через него не восстановится автоматически.

## 8. Как отменить резервирование без повреждения каскада

Если хочешь вернуть обычную схему с одним зарубежным VPS:

1. В **Xray → Маршрутизация** открой `CASCADE - EXIT`.
2. Удали значение из поля **«Балансировщик»** и верни в поле **«Исходящий тег»** значение `cascade-exit`.
3. Сохрани правило и общую конфигурацию Xray.
4. Открой **Xray → Балансировщики**, удали `cascade-failover` и снова сохрани. Не удаляй чужие балансировщики. Обсерватория, если она больше не требуется никакой стратегии, управляется панелью автоматически.
5. Если резервный `backup-se` тебе больше не нужен и не упоминается в других правилах, удали его из **Xray → Исходящие**, сохрани Xray. Отдельный клиент резервного сервера можно после этого отключить на том VPS.

!!! warning "Перед отключением каскада через меню проекта"
    Менеджер 3X-UI AUTO NGINX учитывает зависимости `cascade-exit` в пользовательских балансировщиках. Если балансировщик ещё ссылается на `cascade-exit`, отключение каскада может быть остановлено, чтобы не оставить сломанные ссылки. **Сначала верни маршрутизацию и убери зависимый балансировщик**, затем при необходимости используй штатное меню «5. Каскад → 4. Отключить».

## Используй третий сервер не только как резерв

Добавленный `backup-se` можно применять и в отдельных маршрутах: например, направлять через него YouTube, выбранного клиента или всё входящее XHTTP, пока остальной трафик работает через финский каскад. Эти сценарии подробно разобраны в [«Маршрутизация в 3x-ui»](routing.md).
