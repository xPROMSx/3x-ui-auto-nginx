# Отключение входа по паролю через SSH

Если ты уже настроил SSH-ключ, рекомендуем запретить вход по паролю. Тогда автоматический подбор пароля учётной записи не позволит подключиться к VPS через SSH. Для обычного личного сервера это один из самых полезных шагов защиты.

Инструкция подходит для **Ubuntu 24.04 LTS и 26.04 LTS**. Она не удаляет системный пароль: он может по-прежнему понадобиться для `sudo` или входа через консоль хостера. Настройки разрешения прямого входа root, SSH-порт, существующие ключи и firewall не меняются.

## Перед началом

!!! danger "Сначала проверь вход по ключу"
    Не отключай пароль, пока не убедишься, что можешь открыть новое SSH-подключение по ключу и получить права root. Сохрани резервную копию закрытого ключа. Оставь текущий рабочий SSH-сеанс открытым до завершения всех проверок. Желательно заранее проверить доступ к аварийной консоли VPS в личном кабинете хостера.

Если ключа пока нет, сначала выполни [инструкцию по SSH-ключам через Termius или Windows](ssh-keys.md).

На VPS подключись под своей обычной SSH-учётной записью. Если это не root, выполни:

```bash
sudo -i
```

Проверь, что работаешь от root:

```bash
whoami
```

Ожидаемый ответ: `root`. Все дальнейшие серверные команды выполняются в этом сеансе от root.

Инструкция рассчитана на штатный OpenSSH в Ubuntu. Если ты или хостер настроили дополнительные правила `Match` (отдельные условия для пользователей или адресов), нестандартные файлы конфигурации или двухфакторный вход через SSH, сначала проверь их: общие настройки могут быть переопределены для отдельных подключений, а отключение интерактивной аутентификации может затронуть второй фактор.

**Выбери один из двух способов.** Они создают один и тот же файл. Выполнять оба не нужно.

- [Способ 1. Настройка вручную](#method-manual) - создай файл и примени настройки самостоятельно.
- [Способ 2. Готовый скрипт](#method-script) - скопируй один блок команд.

Для обоих способов: [как отменить изменение](#password-rollback) · [заключительная проверка](#password-check).

## Способ 1. Настройка вручную {#method-manual}

### 1. Создай отдельный файл настроек

В Ubuntu основной файл SSH-сервера находится в `/etc/ssh/sshd_config`. Обычно он подключает дополнительные файлы из `/etc/ssh/sshd_config.d/` в начале конфигурации. OpenSSH читает их в алфавитном порядке и для большинства параметров использует первое найденное значение.

Поэтому создадим файл `00-3x-ui-no-password.conf`, который будет прочитан раньше типичного файла cloud-init. Это позволяет не редактировать оригинальные настройки хостера и легко отменить изменение.

Сначала проверь, существует ли файл:

```bash
ls -l /etc/ssh/sshd_config.d/00-3x-ui-no-password.conf
```

Если файл уже существует, не перезаписывай его вслепую. Если его нет (сообщение о том, что файл не найден), открой редактор:

```bash
nano /etc/ssh/sshd_config.d/00-3x-ui-no-password.conf
```

Вставь три строки:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
```

- `PubkeyAuthentication yes` разрешает вход по SSH-ключам.
- `PasswordAuthentication no` запрещает обычный парольный вход.
- `KbdInteractiveAuthentication no` запрещает интерактивную аутентификацию, через которую сервер также может запрашивать пароль.

В nano нажми **Ctrl+O**, затем **Enter** для сохранения и **Ctrl+X** для выхода.

### 2. Проверь конфигурацию до применения

```bash
sshd -t
```

При успехе команда ничего не выводит. Если появилась ошибка, **не применяй изменения**: исправь файл или удали его по [инструкции отката](#password-rollback).

Теперь проверь, какие параметры реально получит OpenSSH из всех файлов:

```bash
sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|authenticationmethods) '
```

Для обычного сервера ожидается:

``` { .text .no-copy }
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
authenticationmethods any
```

Порядок строк может отличаться. Значение `authenticationmethods publickey` тоже подходит: оно требует вход по ключу. Если значения не совпадают или вывод отсутствует, не продолжай. Проверь приоритет других файлов и настройки хостера. При наличии правил `Match` требуется дополнительно проверить параметры конкретного подключения (см. документацию OpenSSH ниже).

### 3. Примени изменения

Только после успешной проверки выполни:

```bash
systemctl reload ssh.service
```

Команда перечитывает конфигурацию SSH-сервера. Перезагружать VPS не нужно. Не закрывай старый сеанс. Перейди сразу к [заключительной проверке входа](#password-check). Второй способ выполнять не нужно.

## Способ 2. Готовый скрипт {#method-script}

Если не хочешь редактировать файл вручную, скопируй весь блок и выполни его **на VPS от root** в уже открытом рабочем SSH-сеансе. Перед запуском обязательно проверь новый вход по ключу, как описано выше.

Скрипт сначала записывает настройки во временный файл, затем создаёт отдельный файл конфигурации без перезаписи существующего. Проверяет синтаксис и итоговые общие параметры SSH и только затем перечитывает конфигурацию. При ошибке пытается удалить созданный файл; если применение не удалось, дополнительно перечитывает прежнюю конфигурацию. Если откат не подтверждён, не закрывай рабочий сеанс.

```bash
bash <<'EOF'
set -e
file=/etc/ssh/sshd_config.d/00-3x-ui-no-password.conf

if [ "$(id -u)" -ne 0 ]; then
    echo "Ошибка: выполни sudo -i и повтори запуск."
    exit 1
fi

if [ -e "$file" ] || [ -L "$file" ]; then
    echo "Файл уже существует: $file. Проверь его вручную."
    exit 1
fi

sshd -t
umask 077
tmp=$(mktemp "${file}.XXXXXX")
trap 'rm -f -- "$tmp"' EXIT
cat > "$tmp" <<'CONF'
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
CONF
ln -T -- "$tmp" "$file"

if ! sshd -t ||
   ! config=$(sshd -T) ||
   ! grep -qx 'pubkeyauthentication yes' <<< "$config" ||
   ! grep -qx 'passwordauthentication no' <<< "$config" ||
   ! grep -qx 'kbdinteractiveauthentication no' <<< "$config" ||
   ! grep -Eq '^authenticationmethods (any|publickey)$' <<< "$config"; then
    if rm -- "$file"; then
        echo "Ошибка проверки SSH. Созданный файл удалён; reload не выполнялся."
    else
        echo "Не удалось удалить $file. Не закрывай текущий сеанс."
    fi
    exit 1
fi

if ! systemctl reload ssh.service; then
    if rm -- "$file" && sshd -t && systemctl reload ssh.service; then
        echo "Ошибка применения SSH. Прежняя конфигурация перечитана."
    else
        echo "Откат SSH не подтверждён. Не закрывай текущий сеанс. Проверь $file и службу ssh.service."
    fi
    exit 1
fi

echo "Настройки применены. Проверь новый вход по SSH-ключу."
EOF
```

Сообщение об успешном применении означает, что сервер принял настройки. Оно не заменяет проверку нового SSH-подключения. Перейди к [заключительной проверке](#password-check).

## Заключительная проверка {#password-check}

### 1. Убедись, что ключ работает

На компьютере или телефоне открой **новое** подключение к тому же VPS в Termius с выбранным ключом. Если используешь PowerShell, подключись по инструкции [проверки входа по ключу](ssh-keys.md#powershell-key-check).

В новом терминале убедись, что вошёл под правильным пользователем. Если это не root, проверь также, что можешь выполнить `sudo -i`. Парольная фраза закрытого ключа и запрос пароля от sudo не означают, что парольный вход по SSH остался включён.

### 2. Убедись, что вход по паролю запрещён

Сначала на VPS от root повтори проверку:

```bash
sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication) '
```

Ожидается `pubkeyauthentication yes`, `passwordauthentication no` и `kbdinteractiveauthentication no`.

!!! warning "Не повторяй неудачные подключения много раз"
    Если при установке 3X-UI AUTO NGINX ты включил расширенную безопасность VPS, Fail2ban может временно заблокировать твой IP-адрес за неудачные попытки SSH-входа. Одной проверки достаточно. Не перебирай пароли и не повторяй команду, если сервер уже ответил отказом. Сохраняй старый рабочий сеанс.

На **своём компьютере в PowerShell или другом терминале с OpenSSH**, а не на VPS, выполни:

```bash
ssh -o ControlPath=none -o BatchMode=no -o PubkeyAuthentication=no -o PasswordAuthentication=yes -o KbdInteractiveAuthentication=yes -o PreferredAuthentications=password,keyboard-interactive -o NumberOfPasswordPrompts=1 root@IP_ТВОЕГО_VPS
```

Подставь IP VPS и пользователя, под которым успешно входил по ключу. Если прямой root-вход запрещён, используй свою учётную запись, например `ubuntu`. При нестандартном SSH-порте добавь `-p ПОРТ` после `ssh`.

Эта команда открывает новое соединение, не используя уже открытый SSH-сеанс, и намеренно отключает использование ключа на стороне клиента. Она разрешает парольные методы на стороне клиента, чтобы проверить, предлагает ли их сервер. На обычном сервере с отключённым паролем она завершится сообщением наподобие:

``` { .text .no-copy }
Permission denied (publickey).
```

Если сервер запрашивает пароль учётной записи или интерактивный код, либо в списке доступных методов в сообщении об отказе есть `password` или `keyboard-interactive`, не вводи пароль: прерви команду через Ctrl+C и проверь конфигурацию. Таймаут или отказ TCP-соединения сами по себе не доказывают, что парольный вход отключён.

Если новое подключение по ключу работает, права администратора доступны, а парольный вход отклоняется, настройка завершена. Теперь можно закрыть старый сеанс.

## Где хранится файл и как отменить изменение {#password-rollback}

Оба способа создают один файл:

```text
/etc/ssh/sshd_config.d/00-3x-ui-no-password.conf
```

Чтобы отменить именно эту настройку, **из оставленного открытым рабочего сеанса от root** удали созданный этой инструкцией файл и перечитай конфигурацию:

```bash
rm -- /etc/ssh/sshd_config.d/00-3x-ui-no-password.conf &&
sshd -t && systemctl reload ssh.service
```

Не удаляй другие файлы из `sshd_config.d`. После удаления вернутся настройки из остальных файлов, поэтому парольный вход восстановится только если он был разрешён ранее. Если вход по ключу после изменения не работает, выполни этот откат до закрытия старого сеанса. При потере всех SSH-сеансов используй аварийную консоль хостера.
