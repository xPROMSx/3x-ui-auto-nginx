# Backup, полное восстановление и перенос клиентов

## Два способа сохранить свой сервер

3X-UI AUTO NGINX включает **Backup / Restore v3**: резервную копию управляемого стека можно сохранить вне VPS, перенести к другому хостеру и восстановить работающие сервисы. Это помогает, если сервер вышел из строя, хочется переехать в другой дата-центр или нужно заново развернуть ту же конфигурацию.

Начиная с v2.8.0, в меню есть ещё один режим: **восстановление только клиентов и подписок**. Он предназначен для другой задачи - создать свежую установку проекта и перенести в неё своих пользователей, не заменяя всю новую серверную конфигурацию старой. **Новая установка создаёт случайные пути подписок, а импорт возвращает прежние пути RAW и JSON из Backup v3.** Благодаря этому пользователям не придётся получать новые ссылки только из-за переустановки.

| Твоя цель | Какую операцию выбрать |
| --- | --- |
| Переехать к другому хостеру, сохранив управляемый стек, настройки и клиентов | **[Полный Backup v3 → Restore](#full-restore)** |
| Установить новую версию проекта с нуля, но сохранить пользователей | **[Свежая установка → Восстановить клиентов и подписки](#import-clients)** |
| Сохранить копию на случай аварии | **[Создать Backup](#create-backup)** и перенести архив с VPS на свой компьютер |

## Что входит в полный Backup v3

Резервная копия сохраняет управляемые проектом данные, необходимые для восстановления конфигурации:

- **3x-ui и Xray:** базу панели, настройки подключений, клиентов и подписок, поддерживаемую статистику и правила маршрутизации.
- **nginx:** управляемые конфигурации и маршруты к панели, подпискам и прокси-подключениям.
- **HTTPS и сертификаты:** управляемые сертификаты и связанные с ними данные, нужные восстановлению.
- **AdGuard Home:** его настройки и данные, если этот компонент установлен.
- **Дополнительные компоненты проекта:** сайты-прикрытия, каскад и другие поддерживаемые управляемые настройки, если они есть.

Таким образом, **полное Restore возвращает работоспособность управляемого проектом сервера**, а не только список клиентов. Можно восстановить проект на другом VPS, перенаправить домены на новый IP и продолжить пользоваться подключениями.

Операционная система, её SSH-ключи, учётные записи, чужие сервисы и произвольные настройки хостера не являются частью переносимого Backup. Подготовка самого нового VPS остаётся отдельным шагом.

!!! warning "Условия полного восстановления"
    На новом VPS должны совпадать **семейство ОС, версия ОС и архитектура процессора** с резервной копией: например, Ubuntu 24.04 x86_64 → Ubuntu 24.04 x86_64. Для Ubuntu 26.04 и Debian 13 правило такое же. Перенос полноценного Backup с Ubuntu 24.04 на Ubuntu 26.04 не является обновлением системы. Поддерживаются архивы Backup v3.

## Часть 1. Создай и сохрани резервную копию {#create-backup}

Результат этой части - проверенный архив на твоём компьютере или в другом защищённом хранилище вне VPS. Выбери один способ создания: [через меню](#backup-menu) или [через терминал](#backup-cli). Затем в обоих случаях [скачай архив](#download-backup).

!!! warning "Архив содержит секреты"
    В нём находятся пароли, данные клиентов и закрытые ключи. Не публикуй его, не передавай посторонним и не меняй права файла на общедоступные. Копия на том же VPS не спасёт при потере сервера.

### Способ 1. Через меню менеджера {#backup-menu}

1. Подключись по SSH к действующему VPS. Если вошёл под обычным пользователем, выполни на VPS `sudo -i`.
2. Открой менеджер: **на VPS от root**, из каталога со скриптом, выполни:

    ```bash
    bash x-ui-latest.sh
    ```

    Если файл не сохранился, скачай его:

    ```bash
    curl -fSL https://github.com/xPROMSx/3x-ui-auto-nginx/releases/latest/download/x-ui-latest.sh -o x-ui-latest.sh && bash x-ui-latest.sh
    ```
3. Выбери русский язык и **«3. Резервные копии» → «1. Создать резервную копию»**.
4. Дождись сообщения «Архив создан и проверен» и запомни полный путь к архиву в `/var/backups/x-ui/`.
5. Перейди к [скачиванию архива](#download-backup).

### Способ 2. Через терминал {#backup-cli}

Если утилита уже установлена, подключись по SSH к действующему VPS и получи права root. Выполни **на VPS от root**:

```bash
x-ui-backup backup
x-ui-backup list
```

В списке появится созданный архив в `/var/backups/x-ui/`. Запомни имя. Для дополнительной проверки без восстановления выполни:

```bash
x-ui-backup inspect /var/backups/x-ui/ИМЯ_АРХИВА.tar.gz
```

Подставь фактическое имя архива. Команда проверяет его и выводит метаданные, ничего не восстанавливая. Теперь [скачай архив](#download-backup).

### Скачай архив на компьютер {#download-backup}

SFTP - передача файлов через SSH. В Termius открой SFTP-подключение к исходному VPS под той же SSH-учётной записью.

- Если входишь как root, перейди в `/var/backups/x-ui/` и скачай нужный файл.
- Если входишь как обычный пользователь (например, `ubuntu`), каталог резервных копий защищён. В отдельном SSH-сеансе **от имени этого пользователя, не root**, создай доступную только ему копию:

```bash
sudo install -m 600 -o "$(id -un)" /var/backups/x-ui/ИМЯ_АРХИВА.tar.gz "$HOME/ИМЯ_АРХИВА.tar.gz"
```

Замени имя в обеих частях команды на фактическое. Используй свободное имя в домашнем каталоге, чтобы не заменить другой файл. Скачай копию из домашнего каталога через SFTP. После проверки скачанного файла удали только временную копию из домашнего каталога, исходный Backup оставь.

Проверь, что скачанный архив имеет то же имя и размер, что на сервере. Храни его в защищённом месте. **Backup сохранён.**

## Часть 2. Полностью восстанови сервер у другого хостера {#full-restore}

Выбери этот сценарий, если новый VPS должен стать полноценной заменой старого. На нём не нужно предварительно устанавливать 3X-UI AUTO NGINX.

!!! danger "Restore заменяет данные целевого VPS"
    Восстановление заменяет управляемый стек и содержимое затрагиваемых каталогов. Используй чистый VPS или заранее сохрани все важные данные. Не выбирай пункт «1. Установка» ради Restore. Восстанавливай только собственный доверенный архив.

### Шаг 1. Подготовь VPS и архив

Арендуй чистый VPS с той же ОС, версией ОС и архитектурой, что указаны в Backup. Если архива ещё нет, [создай и скачай его](#create-backup). Подготовь SSH-доступ и возможность менять DNS-записи прежних доменов.

TWPM (Telegram Web Proxy Manager) обслуживается отдельно: Backup 3X-UI не сохраняет данные самого Telemt. Если на **целевом** VPS уже есть TWPM, полный Restore остановится до изменения данных. Если нужно продолжить, сначала сохрани необходимые данные TWPM отдельно, затем в его меню выбери «6. Удалить Telegram-прокси» и подтверди удаление сертификата (`y`). После Restore TWPM можно установить заново; ссылка Telegram изменится. Если архив создан со старой неподдерживаемой схемой TWPM, следуй сообщению менеджера и создай новый Backup на исходном сервере. [Руководство TWPM](telegram-web-proxy.md).

### Шаг 2. Загрузи архив на новый VPS {#upload-backup}

Подключись к новому VPS по SSH. **От имени SSH-пользователя, до перехода в root**, создай приватный каталог для архива:

```bash
mkdir -m 700 "$HOME/xui-restore"
```

Если каталог уже существует, выбери другое свободное имя. В Termius открой SFTP-подключение к **новому VPS** под тем же пользователем и загрузи архив в созданный каталог (например, `/root/xui-restore/` или `/home/ubuntu/xui-restore/`). Запомни полный путь. Не размещай архив в каталоге сайта.

Вернись в SSH-сеанс. Если вошёл не под root, выполни на VPS:

```bash
sudo -i
```

Установи приватные права на загруженный файл, подставив реальный абсолютный путь, и проверь размер:

```bash
chmod 600 /ПУТЬ/ИМЯ_АРХИВА.tar.gz
ls -lh /ПУТЬ/ИМЯ_АРХИВА.tar.gz
```

### Шаг 3. Запусти восстановление

**На новом VPS от root** скачай и запусти менеджер:

```bash
curl -fSL https://github.com/xPROMSx/3x-ui-auto-nginx/releases/latest/download/x-ui-latest.sh -o x-ui-latest.sh && bash x-ui-latest.sh
```

1. Выбери русский язык, затем **«3. Резервные копии» → «3. Восстановить резервную копию»**.
2. Введи абсолютный путь к загруженному архиву. Если архив уже в списке, можно выбрать его номер.
3. Проверь показанные метаданные: ОС, архитектуру и компоненты.
4. Ответь на вопросы о настройке автоматических обновлений безопасности и Fail2ban, а также включении UFW с защитой доступа по SSH. На Ubuntu 24.04/26.04 для обычного личного VPS рекомендуется включить UFW; при выборе N сохраняется прежнее состояние UFW. При включении автообновлений учитывай возможную ночную перезагрузку в 04:38 по времени VPS.
5. Прочитай предупреждение и для подтверждения введи `YES`. Дождись итогового отчёта. Если на новой ОС ещё выполняется обновление, менеджер дождётся его завершения. Не перезагружай VPS во время Restore.

Ожидаемый итог - `Restore: SUCCESS` и `Overall: SUCCESS`. Если данные восстановлены, но Security завершился частично, проверь SSH, UFW и службы безопасности, а не запускай Restore повторно вслепую.

### Шаг 4. Направь домены на новый VPS и проверь работу

Если IP изменился, обнови записи A и используемые AAAA для прежних доменов панели, REALITY и других восстановленных подключений. Проверь, что домены указывают на новый VPS.

Открой панель по прежнему адресу, проверь Xray, сертификаты, AdGuard Home (если был установлен), подписку и реальное подключение устройства. Если включал UFW, не закрывая текущий SSH-сеанс, проверь новый вход по SSH. При использовании каскада проверь его состояние и трафик.

**Готово:** когда сервисы работают на новом VPS, а устройства подключаются, перенос завершён. Не удаляй старый VPS и архив до этой проверки.

## Часть 3. Перенеси только клиентов и подписки в новую установку {#import-clients}

<small>Возможность v2.8.0</small>

Этот режим нужен, если хочешь получить новую серверную конфигурацию, но сохранить пользователей. Новая установка создаёт случайные пути RAW и JSON для подписок, а импорт возвращает прежние общие пути из Backup v3. При сохранении прежнего домена панели сохраняются и адреса прежних подписок.

!!! danger "Новая установка удаляет прежние управляемые данные"
    Для этого сценария подготовь чистый VPS. Если устанавливаешь проект заново на том же VPS, сначала сохрани проверенный Backup за пределами сервера. Не запускай новую установку поверх важных данных без копии.

### Шаг 1. Сохрани клиентов и подготовь домены

На старом VPS [создай и скачай Backup v3](#create-backup). Если хочешь сохранить старые ссылки подписок, используй прежний домен панели при новой установке и направь его DNS-записи на новый VPS к моменту выпуска сертификата. Учти, что смена DNS временно переключит пользователей на новый сервер; согласуй момент переноса. Для нового домена потребуются новые URL подписок.

### Шаг 2. Установи проект на чистом VPS

Выполни [первый запуск](../start.md) на новом VPS и проверь панель и Xray. Выбери нужные входящие подключения: клиенты из архива будут привязаны к подходящим активным подключениям новой установки. Если не нужен дополнительный тестовый клиент, на вопрос о создании клиента можно ответить N.

### Шаг 3. Загрузи архив и выполни импорт

Подключись по SSH к новому VPS. **От имени SSH-пользователя, до перехода в root**, создай приватный каталог:

```bash
mkdir -m 700 "$HOME/xui-restore"
```

Если каталог уже существует, выбери другое свободное имя. Через SFTP в Termius загрузи архив в этот каталог под тем же пользователем и запомни абсолютный путь. Вернись в SSH-сеанс; если вошёл не под root, выполни `sudo -i`. **На новом VPS от root**, подставив фактический путь, выполни:

```bash
chmod 600 /ПУТЬ/ИМЯ_АРХИВА.tar.gz
ls -lh /ПУТЬ/ИМЯ_АРХИВА.tar.gz
```

Проверь размер архива. Здесь не нужно запускать полное восстановление.

**На новом VPS от root** из каталога со скриптом открой меню:

```bash
bash x-ui-latest.sh
```

Выбери русский язык, затем **«3. Резервные копии» → «4. Восстановить клиентов и подписки»**. Укажи архив, введи текущие данные входа в **новую** панель и код двухфакторной аутентификации (2FA), если она включена. Проверь итоговый отчёт: созданных клиентов, их привязки, пропуски и неполные результаты.

**Что переносится:** клиентские идентификаторы и учётные данные, состояние, лимиты, сроки, поддерживаемые счётчики, общие пути RAW и JSON. Домен, сертификаты, конфигурация входящих и прочая серверная инфраструктура остаются новыми.

Если на новой панели уже есть клиент с совпадающим email или идентификатором подписки, существующая запись сохраняется, а конфликтующая запись из архива пропускается. Проверь отчёт до переключения пользователей.

### Шаг 4. Проверь прежние подписки и подключения {#subscription-check}

Если домен панели сохранился, открой ранее выданную ссылку подписки в клиентском приложении и обнови её: прежний URL должен вернуть актуальные подключения нового VPS. При другом домене передай пользователям новый URL. Подключись с устройства, проверь доступ к сайтам и убедись, что используется новый VPS.

**Готово:** клиенты работают с новой конфигурацией, а при сохранённом домене им не пришлось менять URL подписки.

## Если восстановление или импорт завершились ошибкой

До любой операции сохраняй исходный Backup отдельно. Полный Restore предусматривает проверку nginx и возврат управляемых данных при обнаруженном сбое. Не удаляй архив и диагностические данные, сначала прочитай конкретную ошибку и статус отката.

Импорт клиентов добавляет данные в уже созданную панель, а не заменяет весь стек. Если нужен возврат исходного состояния новой установки, используй отдельно сохранённую резервную копию этой установки.
